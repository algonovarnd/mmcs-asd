# Линейные алгоритмы

Когда в задаче дан массив, очень часто требуется работать не со всем массивом целиком, а с его непрерывными частями. Например, находить сумму на некотором участке или выполнять одно и то же изменение сразу на целом диапазоне позиций. Если каждый раз обрабатывать такой участок напрямую, то даже одна операция может занимать линейное время. Поэтому возникает естественный вопрос: можно ли заранее подготовить некоторую информацию о массиве так, чтобы потом работать с подотрезками существенно быстрее?

Чтобы обсуждать такие приёмы аккуратно, сначала введём несколько базовых понятий.

Пусть дан массив $ a_0, a_1, \dots, a_{n-1} $.

**Префиксом массива** называется его начальная часть. Для каждого $k$, где $ 0 \le k \le n $, префикс длины $ k $ состоит из элементов

$$
a_0, a_1, \dots, a_{k-1}.
$$

При $ k = 0 $ получаем пустой префикс. При $ k = n $ префикс совпадает со всем массивом. Таким образом, у массива из $ n $ элементов ровно $ n+1 $ префикс.

Аналогично, суффиксом массива называется его конечная часть. Для каждого $ k $, где $ 0 \le k \le n $, суффикс, начинающийся в позиции $k$, состоит из элементов

$$
a_k, a_{k+1}, \dots, a_{n-1}.
$$

При $ k = n $ это пустой суффикс. Значит, суффиксов тоже ровно $ n+1 $.

Подотрезком массива будем называть любую непрерывную часть массива. Договоримся записывать подотрезки в виде полуинтервалов $ [l, r) $, где $ 0 \le l \le r \le n $. Такой подотрезок состоит из элементов

$$
a_l, a_{l+1}, \dots, a_{r-1}.
$$

Если $ l = r $, то подотрезок пустой. Такая запись особенно удобна тем, что левая граница входит в отрезок, а правая нет. В дальнейшем это заметно упрощает работу с индексами и помогает избежать путаницы в формулах и в коде. Более того, длина отрезка (количество элементов в нем) вычисялется довольно просто: $ (r - l) $.

С этими определениями связано простое, но важное наблюдение. Любой подотрезок $ [l, r) $ можно рассматривать как суффикс префикса $[0, r)$. Действительно, префикс $[0, r)$ состоит из элементов

$$
a_0, a_1, \dots, a_{r-1},
$$

а если отбросить в нём первые $l$ элементов, то останется ровно подотрезок

$$
a_l, a_{l+1}, \dots, a_{r-1}.
$$

Точно так же любой подотрезок $[l, r)$ можно рассматривать как префикс суффикса $[l, n)$: достаточно взять суффикс, начинающийся в позиции $l$, и оставить в нём только первые $r-l$ элементов.

На первый взгляд это наблюдение выглядит почти очевидным, но в дальнейшем оно окажется полезным. Оно показывает, что подотрезок удобно выражать через более крупные объекты — префиксы и суффиксы. В частности, во многих алгоритмах информация будет храниться именно о префиксах, а интересующий нас подотрезок затем будет восстанавливаться через неё.

## Префиксные суммы

Теперь перейдём к первой основной задаче. Пусть требуется быстро находить сумму элементов на подотрезке $[l, r)$. Если делать это напрямую, то для каждого запроса придётся складывать элементы

$$
a_l + a_{l+1} + \dots + a_{r-1},
$$

а значит, время работы одного запроса в худшем случае будет линейным. Если запросов много, такой способ становится слишком медленным.

Попробуем заранее сохранить о массиве такую информацию, которая позволит получать суммы быстро. Для этого введём массив префиксных сумм $p$. Его элементы определяются так:

$$
p_k = a_0 + a_1 + \dots + a_{k-1}
$$

для всех $k$ от $0$ до $n$. Иными словами, $p_k$ — это сумма префикса длины $k$.

Из этого определения сразу видно, как строится массив префиксных сумм. Для пустого префикса сумма равна нулю, то есть

$$
p_0 = 0.
$$

Дальше получаем:

$$
p_1 = a_0 = p_0 + a_0,
$$

$$
p_2 = a_0 + a_1 = p_1 + a_1,
$$

$$
p_3 = a_0 + a_1 + a_2 = p_2 + a_2,
$$

и так далее. Видно, что каждый следующий элемент выражается через предыдущий одной и той же формулой:

$$
p_k = p_{k-1} + a_{k-1}.
$$

Таким образом, массив префиксных сумм можно вычислить за один проход по массиву.

Теперь разберёмся, как с его помощью находить сумму на подотрезке $[l, r)$. По определению,

$$
p_r = a_0 + a_1 + \dots + a_{r-1}.
$$

Это сумма всех элементов от начала массива до позиции $r-1$. Но нам нужна не вся эта сумма, а только её часть, начиная с позиции $l$. Лишними являются элементы

$$
a_0, a_1, \dots, a_{l-1},
$$

и их сумма как раз равна

$$
p_l = a_0 + a_1 + \dots + a_{l-1}.
$$

Если вычесть эту лишнюю часть из $p_r$, то останется именно сумма элементов подотрезка $[l, r)$:

$$
p_r - p_l =
(a_0 + a_1 + \dots + a_{r-1}) - (a_0 + a_1 + \dots + a_{l-1}) =
a_l + a_{l+1} + \dots + a_{r-1}.
$$

Итак, получаем формулу

$$
a_l + a_{l+1} + \dots + a_{r-1} = p_r - p_l.
$$

Её смысл очень прост: сумма на подотрезке находится как разность двух префиксных сумм. Мы берём сумму большого префикса $[0, r)$ и убираем из неё сумму меньшего префикса $[0, l)$. После того как массив $p$ построен, каждый запрос суммы обрабатывается за $O(1)$.

Теперь рассмотрим задачу другого типа. Пусть требуется выполнять операции вида: прибавить число $x$ ко всем элементам подотрезка $[l, r)$. Если делать это напрямую, то одна такая операция потребует изменить элементы $a_l, a_{l+1}, \dots, a_{r-1}$, то есть в худшем случае снова займёт линейное время. Если таких операций много, прямой способ оказывается слишком дорогим.

Здесь тоже хочется не выполнять каждое изменение сразу полностью, а хранить его в более компактном виде. Чтобы понять, как это сделать, полезно посмотреть не на сами значения массива, а на то, как они меняются при переходе от одной позиции к следующей.

Введём массив $d$, который будем называть разностным. Положим

$$
d_0 = a_0,
$$

а для всех $i \ge 1$ определим

$$
d_i = a_i - a_{i-1}.
$$

Таким образом, $d_i$ показывает, насколько значение в позиции $i$ отличается от предыдущего значения. Если известен массив $d$, то исходный массив $a$ можно восстановить. Действительно,

$$
a_0 = d_0,
$$

$$
a_1 = a_0 + d_1 = d_0 + d_1,
$$

$$
a_2 = a_1 + d_2 = d_0 + d_1 + d_2,
$$

и вообще

$$
a_i = d_0 + d_1 + \dots + d_i.
$$

Иначе говоря, массив $a$ является массивом префиксных сумм для массива $d$. Это очень важный момент: разностный массив и префиксные суммы тесно связаны друг с другом.

Теперь посмотрим, что произойдёт с массивом $d$, если мы прибавим число $x$ ко всем элементам подотрезка $[l, r)$. После такой операции элементы с индексами от $l$ до $r-1$ увеличатся на $x$, а все остальные останутся без изменений.

Рассмотрим сначала позицию $l$. Если до неё значения не менялись, а начиная с неё все увеличились на $x$, то именно в этой точке должно появиться дополнительное увеличение на $x$. Значит, в разностном массиве нужно сделать

$$
d_l \mathrel{+}= x.
$$

Теперь посмотрим на позицию $r$, если $r < n$. До позиции $r-1$ элементы были увеличены на $x$, а начиная с позиции $r$ увеличение должно прекратиться. Значит, в точке $r$ нужно сделать обратное изменение, то есть

$$
d_r \mathrel{-}= x.
$$

Больше ничего менять не нужно. Таким образом, операция прибавления $x$ на всём подотрезке $[l, r)$ сводится к двум изменениям в разностном массиве:

$$
d_l \mathrel{+}= x,
$$

$$
d_r \mathrel{-}= x \quad \text{при } r < n.
$$

После того как все такие операции выполнены, исходный массив восстанавливается обычным префиксным суммированием массива $d$.

Почему это работает, полезно ещё раз понять содержательно. В позиции $l$ мы как бы запускаем прибавку $x$: начиная с этой точки все последующие префиксные суммы становятся больше на $x$. В позиции $r$ мы эту прибавку останавливаем: начиная с неё лишнее $x$ компенсируется. Поэтому итоговое изменение действует ровно на нужном полуинтервале $[l, r)$.

Итак, префиксные суммы и разностный массив выражают одну и ту же общую идею. В первом случае мы заранее накапливаем значения, чтобы быстро отвечать на запросы о подотрезках. Во втором случае мы заранее накапливаем изменения, чтобы быстро выполнять массовые обновления. В обоих случаях ключевую роль играет работа с префиксами: именно она позволяет заменить большое число локальных действий одним линейным проходом по массиву.

## Сохранение информации на префиксе

После того как мы научились работать с подотрезками через префиксы, возникает следующий естественный шаг. В предыдущем разделе мы использовали префиксные суммы как инструмент: заранее посчитали массив $p$ и дальше быстро отвечали на запросы.

Теперь идея становится шире: на префиксе можно хранить не только суммы, а вообще любую полезную информацию. Если мы умеем поддерживать эту информацию при движении слева направо, то в момент, когда мы стоим в позиции $r$, вся информация о возможных левых границах уже доступна.

Рассмотрим это на простой задаче. Пусть дан массив, и нужно максимизировать разность

$$
a_j - a_i \quad \text{при } i < j.
$$

Если перебирать все пары, получаем $O(n^2)$. Попробуем посмотреть на задачу иначе.

Будем фиксировать правый элемент $j$ и зададим себе вопрос: какой $i$ даёт наилучший ответ?

Для фиксированного $j$ выражение $a_j - a_i$ максимально тогда, когда $a_i$ минимально. Значит, нам нужен минимум на префиксе $[0, j)$.

Это приводит к простому алгоритму. Идём слева направо и поддерживаем величину

$$
mn = \min(a_0, a_1, \dots, a_{j-1}).
$$

Тогда для текущего $j$ кандидат на ответ равен

$$
a_j - mn.
$$

После этого обновляем $mn$, сравнивая его с $a_j$, и идём дальше.

Важно зафиксировать, что именно здесь происходит. Мы не перебираем левую границу. Мы заранее сохранили на префиксе всю нужную информацию — в данном случае минимум — и используем её за $O(1)$ для каждого $j$. Весь алгоритм работает за $O(n)$.

Теперь немного усложним задачу. Пусть требуется максимизировать ту же разность, но с ограничением

$$
j - i \ge k.
$$

Если снова зафиксировать $j$, то допустимые $i$ должны удовлетворять условию

$$
i \le j - k.
$$

Значит, все возможные $i$ лежат в диапазоне индексов от $0$ до $j-k$ включительно. В терминах полуинтервалов это множество записывается как

$$
[0,, j-k+1).
$$

Именно на этом префиксе нам нужно поддерживать минимум.

Алгоритм практически не меняется. Мы всё так же идём слева направо, но теперь минимум обновляется не сразу, а с задержкой. Когда мы переходим к позиции $j$, в допустимую область впервые попадает элемент $a_{j-k}$. Именно его нужно учесть при обновлении минимума.

Таким образом, мы поддерживаем минимум на префиксе, но только на той его части, которая уже стала допустимой. Снова получается линейное время.

Здесь важно увидеть обобщение: мы по-прежнему фиксируем правую границу и используем информацию о левой, но теперь область допустимых левых границ меняется со временем. Тем не менее, если эта область расширяется монотонно, мы всё равно можем поддерживать нужную информацию за $O(1)$ на шаг.

Перейдём к другой задаче. Пусть требуется найти подотрезок с максимальной суммой.

Если рассматривать подотрезок $[l, r)$, его сумма равна

$$
p_r - p_l,
$$

где $p$ — массив префиксных сумм.

Теперь снова зафиксируем правую границу $r$. Тогда задача сводится к выбору такого $l < r$, при котором выражение

$$
p_r - p_l
$$

максимально.

Для фиксированного $r$ это происходит тогда, когда $p_l$ минимально. Значит, нам нужно знать минимум префиксных сумм на префиксе $[0, r)$.

Алгоритм полностью повторяет предыдущие рассуждения. Идём слева направо, поддерживаем

$$
mn = \min(p_0, p_1, \dots, p_{r-1}),
$$

и на каждом шаге считаем кандидат

$$
p_r - mn.
$$

После этого обновляем минимум.

Таким образом, задача о максимальной сумме подотрезка сводится к той же самой идее: фиксируем правую границу и используем заранее сохранённую информацию о префиксе.

Во всех рассмотренных задачах используется один и тот же принцип. Мы двигаемся слева направо, в каждый момент фиксируем правую границу и храним на префиксе некоторую характеристику (минимум, максимум, сумму или что-то более сложное). Благодаря этому левая граница не перебирается явно — она уже «закодирована» в накопленной информации.

Именно этот приём — сохранение нужной информации на префиксе — лежит в основе большого числа линейных алгоритмов.


## Метод двух указателей

Переходим к следующему приёму, который на первый взгляд выглядит иначе, но по сути продолжает ту же самую идею — мы всё так же работаем с подотрезками и стараемся не пересчитывать информацию заново.

Речь пойдёт о методе двух указателей.

В предыдущем разделе мы фиксировали правую границу и использовали информацию о префиксе. Теперь будем явно рассматривать подотрезок $[l, r)$ и двигать обе его границы.

Пусть у нас есть некоторый текущий подотрезок $[l, r)$. Мы будем изменять его, сдвигая либо правую границу $r$, либо левую границу $l$, и при этом поддерживать некоторую характеристику этого подотрезка — например, сумму элементов.

Ключевое условие, при котором такой подход работает, связано с монотонностью.

Если зафиксировать левую границу $l$ и двигать правую границу $r$ вправо, то подотрезок расширяется. Во многих задачах при этом интересующая нас величина изменяется монотонно. Например, сумма подотрезка не убывает, если все элементы неотрицательны.

С другой стороны, если зафиксировать правую границу $r$ и двигать левую границу $l$ вправо, то подотрезок сужается, и та же величина изменяется в противоположную сторону (в случае суммы — не возрастает).

Именно эта согласованная монотонность позволяет не возвращаться назад и не перебирать границы заново. Каждый указатель движется только вперёд, поэтому суммарное число шагов остаётся линейным.

Рассмотрим это на задаче: найти подотрезок с суммой ровно $x$. Будем считать, что все элементы массива неотрицательны — это как раз гарантирует нужную монотонность.

Будем поддерживать текущий подотрезок $[l, r)$ и его сумму $s$. Изначально $l = 0$, $r = 0$, $s = 0$.

Далее начинаем двигать правую границу. На каждом шаге увеличиваем $r$ и добавляем в сумму новый элемент:

$$
s \mathrel{+}= a_r.
$$

После этого возможны три ситуации.

Если $s < x$, то подотрезок пока слишком «мал», и нужно продолжать увеличивать $r$.

Если $s = x$, то мы нашли подходящий подотрезок $[l, r)$.

Если $s > x$, то подотрезок стал слишком «большим». Поскольку все элементы неотрицательны, дальнейшее увеличение $r$ только увеличит сумму. Значит, нужно уменьшать подотрезок, двигая левую границу $l$:

$$
s \mathrel{-}= a_l,\quad l \mathrel{+}= 1.
$$

И так до тех пор, пока сумма снова не станет $\le x$.

Важно понимать, что при таком процессе каждая из границ $l$ и $r$ проходит массив не более одного раза. Мы никогда не двигаем указатели назад. Поэтому общее время работы — $O(n)$.

Содержательно этот метод отличается от предыдущего раздела тем, что мы больше не храним информацию о всём префиксе. Вместо этого мы храним информацию только о текущем подотрезке и поддерживаем её при изменении его границ.

Тем не менее, общий принцип остаётся тем же: мы не перебираем все подотрезки. Мы поддерживаем инвариант (в данном случае — текущую сумму и условия на неё) и последовательно перебираем только те состояния, которые могут привести к ответу.

Метод двух указателей применим тогда, когда при движении границ характеристика подотрезка ведёт себя монотонно. В этом случае удаётся организовать процесс так, что каждая граница двигается только вперёд, и вся задача решается за линейное время.

Давай перепишем этот фрагмент так, чтобы было явно понятно, **почему именно здесь работает метод двух указателей**, а не просто «что делать».

Рассмотрим более содержательный пример, где поддерживаемая информация уже не сводится к одной числовой величине.

Пусть дан массив $a_0, a_1, \dots, a_{n-1}$, где $a_i$ — это тип дерева. Требуется найти подотрезок минимальной длины, в котором встречаются все различные типы деревьев, присутствующие в массиве.

Обозначим через $T$ количество различных значений во всём массиве. Тогда подотрезок $[l, r)$ является подходящим, если на нём встречаются все $T$ типов.

Будем рассматривать текущий подотрезок $[l, r)$ и поддерживать информацию о нём. Для этого храним массив $cnt$, где $cnt[x]$ — количество вхождений типа $x$ в текущем окне, а также число различных типов в окне $cur$.

Теперь важно понять, почему здесь вообще можно применить два указателя.

Рассмотрим поведение величины $cur$ при движении границ.

Если мы фиксируем $l$ и двигаем правую границу $r$ вправо, то подотрезок расширяется. При этом новые элементы могут только добавлять новые типы, но не удалять старые. Значит, $cur$ не убывает.

Если же мы фиксируем $r$ и двигаем левую границу $l$ вправо, то подотрезок сужается. При этом мы можем только терять типы, но не получать новые. Значит, $cur$ не возрастает.

Таким образом, свойство «подотрезок содержит все $T$ типов» ведёт себя монотонно:

* при расширении окна оно может стать истинным,
* при сжатии — может стать ложным,
* но не происходит «скачков» туда-обратно при фиксированной другой границе.

Именно это и позволяет применить метод двух указателей. Мы можем для каждой правой границы $r$ найти минимальную левую границу $l$, при которой условие выполняется, и при этом не возвращаться назад.

Теперь опишем сам алгоритм.

Двигаем правую границу $r$, расширяя подотрезок, и обновляем $cnt$ и $cur$. Пока $cur < T$, подотрезок ещё не содержит всех типов.

Как только $cur = T$, подотрезок стал подходящим. Теперь фиксируем $r$ и начинаем двигать левую границу $l$, пытаясь сделать подотрезок минимальным.

При каждом сдвиге $l$:

* уменьшаем $cnt[a_l]$,
* если $cnt[a_l]$ стало равно нулю, уменьшаем $cur$.

Пока после сдвига остаётся $cur = T$, подотрезок всё ещё содержит все типы, и его можно продолжать сжимать.

В тот момент, когда $cur$ становится меньше $T$, условие перестаёт выполняться. Это означает, что предыдущий подотрезок (до сдвига $l$) был минимальным для текущего $r$. Его длину можно учесть как кандидат на ответ.

После этого снова начинаем двигать правую границу.

Почему алгоритм работает за $O(n)$: каждая граница $l$ и $r$ проходит массив не более одного раза. Мы никогда не возвращаем указатели назад, потому что монотонность свойства гарантирует, что найденная граница $l$ больше не понадобится для меньших $r$.

Таким образом, здесь метод двух указателей работает именно потому, что условие «в подотрезке есть все типы» изменяется монотонно при движении границ, и это позволяет последовательно перебрать все кандидаты без повторных вычислений.

# Линейные структуры данных

В первой части мы обсуждали линейные алгоритмы, то есть такие алгоритмы, в которых данные обычно просматриваются последовательно, а нужная информация накапливается по ходу обработки. Теперь возникает следующий естественный вопрос: в каком виде эти данные удобно хранить, если мы хотим быстро выполнять такие последовательные операции?

Здесь и появляются линейные структуры данных.

Линейной структурой данных называется такая структура, в которой элементы расположены последовательно, друг за другом. Иначе говоря, они образуют одну цепочку. У каждого элемента, кроме, возможно, первого и последнего, есть ровно один сосед слева и ровно один сосед справа.

Важно понимать, что линейность структуры не означает единственный способ доступа к её элементам. Например, в массиве элементы тоже расположены последовательно, но доступ к ним произвольный: по индексу можно сразу обратиться к любой позиции. В других линейных структурах, напротив, операции естественным образом ограничены только концами последовательности. Именно к таким структурам относятся стек, очередь и дек.

Во всех этих случаях элементы всё равно образуют одну линию, одну последовательность. Различие состоит лишь в том, какие операции над этой последовательностью разрешены и как именно они реализуются.

## Стек

Стек устроен по очень естественному принципу: элементы добавляются и удаляются только с одного конца. Этот конец обычно называют вершиной стека. Поэтому если в стек подряд положить несколько элементов, то первым извлечётся тот, который был добавлен последним. Именно это имеют в виду, когда говорят, что стек работает по принципу «последним пришёл — первым вышел».

Если представить себе стопку книг, то аналогия будет почти точной. Новую книгу удобно положить только сверху. Снять книгу из середины, не потревожив остальные, уже нельзя. Со стеком происходит то же самое: разрешены только операции на вершине.

Обычно у стека есть три основные операции. Первая — добавить элемент в стек (`push`). Вторая — удалить верхний элемент (`pop`). Третья — посмотреть значение верхнего элемента, не удаляя его (`top`).

Теперь рассмотрим задачу, которая делает стек существенно интереснее. Пусть требуется поддерживать стек и дополнительно уметь за $O(1)$ находить минимальный элемент среди всех элементов, которые сейчас лежат в стеке.

Если каждый раз искать минимум перебором, получим $O(n)$, что слишком медленно. Значит, минимум нужно уметь поддерживать «на лету», вместе с обычными операциями.

Разберёмся, как изменяется минимум при добавлении нового элемента $x$.

Если стек был пуст, то минимум равен $x$.

Если стек не пуст, то новый минимум — это минимум из двух значений:

* прежнего минимума,
* элемента $x$.

То есть при добавлении элемента новый минимум можно вычислить сразу, если мы знаем предыдущий.

Это приводит к следующей идее: будем хранить в стеке не просто значения, а пары. Для каждого элемента будем запоминать:

* его значение,
* минимум среди всех элементов стека от дна до этой позиции.

Тогда вершина стека будет содержать не только верхний элемент, но и минимум для всего текущего стека.

Разберём это на примере. Пусть мы последовательно добавляем элементы:

$5, 2, 7, 1$.

Тогда в стеке будут храниться такие пары:

* после добавления `5`: $(5, 5)$,
* после добавления `2`: $(2, 2)$,
* после добавления `7`: $(7, 2)$,
* после добавления `1`: $(1, 1)$.

Второй компонент каждой пары — это минимум на всём стеке к данному моменту.

Теперь видно, как работать с такой структурой.

При `push(x)`:

* если стек пуст, кладём пару $(x, x)$,
* иначе берём минимум из $x$ и минимума, записанного в предыдущем элементе, и кладём пару $(x, new_min)$.

При `pop()`:

* просто удаляем верхнюю пару.

При запросе минимума:

* берём второй компонент верхней пары.

Все операции по-прежнему работают за $O(1)$.

Ниже приведена реализация такого стека на C++.

```cpp
struct StackMin {
    static const int MAXN = 100000;

    struct Node {
        int value;
        int mn;
    };

    Node st[MAXN];
    int sz = 0;

    bool empty() const {
        return sz == 0;
    }

    int size() const {
        return sz;
    }

    void push(int x) {
        if (sz == MAXN) {
            throw runtime_error("Stack overflow");
        }

        if (empty()) {
            st[sz] = {x, x};
        } else {
            st[sz] = {x, min(x, st[sz - 1].mn)};
        }
        sz++;
    }

    void pop() {
        if (empty()) {
            throw runtime_error("Stack is empty");
        }
        sz--;
    }

    int top() const {
        if (empty()) {
            throw runtime_error("Stack is empty");
        }
        return st[sz - 1].value;
    }

    int get_min() const {
        if (empty()) {
            throw runtime_error("Stack is empty");
        }
        return st[sz - 1].mn;
    }
};
```

Важно понять, почему эта идея корректна.

Для каждой позиции в стеке мы храним минимум среди всех элементов до этой позиции включительно. Поэтому у верхнего элемента второй компонент всегда равен минимуму по всему стеку. Когда верхний элемент удаляется, новая вершина уже содержит правильный минимум для оставшейся части стека. Ничего пересчитывать не требуется.

Здесь хорошо видно тот же приём, что и в предыдущей части: вместе с элементами структуры мы храним агрегированную информацию о её «префиксе», благодаря чему можем быстро отвечать на дополнительные запросы.


Рассмотрим задачу проверки правильности скобочной последовательности. Пусть дана строка, состоящая из символов `(`, `)`, `[`, `]`, `{`, `}`. Требуется определить, является ли она корректной.

Под корректностью будем понимать следующее:

* каждая открывающая скобка должна быть закрыта,
* тип скобок должен совпадать,
* порядок должен быть правильным: последняя открытая скобка закрывается первой.

Последнее условие является ключевым. Например, последовательность `([)]` некорректна, хотя в ней равное число открывающих и закрывающих скобок. Проблема в порядке закрытия.

Попробуем понять, какую информацию нужно хранить при просмотре строки слева направо.

Когда мы встречаем открывающую скобку, она ещё не закрыта. Значит, её нужно «запомнить», чтобы позже проверить соответствующую закрывающую. Более того, если открыто несколько скобок подряд, закрываться они должны в обратном порядке. Это и есть поведение стека.

Будем использовать стек, в который кладём открывающие скобки.

Идём по строке слева направо.

* Если встречаем открывающую скобку (`(`, `[`, `{`), кладём её в стек.
* Если встречаем закрывающую скобку:

  * если стек пуст, значит, нет соответствующей открывающей — последовательность некорректна;
  * иначе берём верхний элемент стека и проверяем, что он соответствует типу текущей скобки (например, `(` соответствует `)`).
  * если не соответствует — последовательность некорректна;
  * если соответствует — удаляем этот элемент из стека.

После обработки всей строки стек должен оказаться пустым. Если в нём остались элементы, значит, есть незакрытые скобки.

Почему этого достаточно для корректности?

В каждый момент стек содержит все открывающие скобки, которые ещё не были закрыты. Причём их порядок в стеке отражает порядок вложенности: самая «внутренняя» скобка находится на вершине. Когда приходит закрывающая скобка, она обязана закрыть именно последнюю открытую — иначе нарушается вложенность. Это и проверяется сравнением с вершиной стека.

Таким образом, стек точно моделирует структуру вложенности скобок, и алгоритм корректен.

Рассмотрим теперь задачу вычисления значения выражения в постфиксной записи.

В постфиксной (обратной польской) записи оператор записывается после своих операндов. Например,

$$
(2 + 3) \cdot 4
$$

записывается как

$$
2\ 3\ +\ 4\ \cdot
$$

Главное свойство такой записи — в ней нет скобок, и порядок вычислений однозначен.

Попробуем понять, как вычислять такое выражение, двигаясь слева направо.

Когда мы встречаем число, оно ещё не участвует ни в какой операции. Поэтому его нужно временно сохранить. Для этого удобно использовать стек.

Когда мы встречаем оператор, например `+`, это означает, что нужно взять два последних числа, применить операцию и положить результат обратно.

Алгоритм получается следующим.

Идём по выражению слева направо.

* Если текущий токен — число, кладём его в стек.
* Если текущий токен — операция:

  * извлекаем из стека верхний элемент — это правый операнд,
  * извлекаем следующий — это левый операнд,
  * применяем операцию,
  * результат кладём обратно в стек.

В конце в стеке останется ровно одно значение — результат выражения.

Почему это работает?

В каждый момент стек содержит значения подвыражений, которые уже полностью вычислены, но ещё не использованы в более крупных выражениях. Когда встречается оператор, он «сворачивает» два последних подвыражения в одно. Стек тем самым хранит границу между уже обработанной частью выражения и тем, что ещё предстоит использовать.

Важно, что порядок извлечения операндов фиксирован: сначала извлекается правый, затем левый. Это связано с тем, что стек возвращает элементы в обратном порядке добавления.

Наконец, рассмотрим задачу поиска ближайшего меньшего элемента слева.

Пусть дан массив $a_0, a_1, \dots, a_{n-1}$. Для каждого $i$ требуется найти максимальный индекс $j < i$, такой что

$$
a_j < a_i.
$$

Если такого $j$ нет, будем считать ответ равным, например, $-1$.

Наивное решение — для каждого $i$ идти влево — работает за $O(n^2)$. Попробуем построить линейный алгоритм.

Будем идти по массиву слева направо и поддерживать стек индексов. В этом стеке будем хранить только «полезные» элементы — те, которые ещё могут стать ответом для будущих позиций.

Рассмотрим текущий индекс $i$. Мы хотим найти ближайший слева элемент, который строго меньше $a_i$.

Если на вершине стека находится индекс $j$, такой что $a_j \ge a_i$, то этот элемент не может быть ответом:

* он не меньше $a_i$,
* и, что важнее, он не сможет быть ответом и для будущих элементов, потому что текущий элемент $a_i$ находится правее и не больше него.

Поэтому такие элементы можно удалять из стека.

Итак, алгоритм:

для каждого $i$:

* пока стек не пуст и $a_{\text{top}} \ge a_i$, удаляем верхний элемент;
* после этого:

  * если стек пуст, ответа нет;
  * иначе элемент на вершине — ближайший меньший слева;
* добавляем индекс $i$ в стек.

Почему это работает за $O(n)$?

Каждый индекс добавляется в стек ровно один раз. Удаляется он тоже не более одного раза — после удаления он больше никогда не вернётся. Значит, общее число операций со стеком пропорционально $n$.

Если требуется найти ближайший меньший элемент справа, можно выполнить тот же алгоритм, но пройти массив справа налево.


## Очередь

Перейдём к очереди.

Очередь — это линейная структура данных, в которой элементы добавляются с одного конца, а удаляются с другого. В отличие от стека, здесь работает принцип «первым пришёл — первым вышел».

У очереди есть две основные операции:

* добавление элемента в конец (`push`),
* удаление элемента из начала (`pop`).

Также часто требуется операция получения элемента в начале очереди.

Если попытаться реализовать очередь на массиве «в лоб», возникает проблема: при удалении из начала пришлось бы сдвигать все элементы, что даёт $O(n)$ на операцию. Поэтому используется другой подход.

Идея состоит в том, чтобы реализовать очередь через два стека.

Будем поддерживать два стека:

* первый стек $s_1$ отвечает за добавление элементов,
* второй стек $s_2$ отвечает за удаление.

Когда мы добавляем элемент, просто кладём его в $s_1$.

Когда нужно удалить элемент из очереди, возможны два случая.

Если $s_2$ не пуст, то просто удаляем элемент из его вершины — это и есть начало очереди.

Если $s_2$ пуст, то нужно переложить все элементы из $s_1$ в $s_2$. При этом порядок элементов переворачивается: тот элемент, который был добавлен раньше всех, окажется на вершине $s_2$. После этого можно удалить элемент из $s_2$.

Важно понять, почему такая реализация работает эффективно.

Каждый элемент сначала попадает в $s_1$, затем ровно один раз переносится в $s_2$, и после этого удаляется. То есть каждый элемент участвует в константном числе операций. Поэтому, несмотря на то что отдельная операция может выглядеть как $O(n)$ (когда происходит перенос), в среднем каждая операция выполняется за $O(1)$. Это называется амортизированной сложностью.

Теперь усложним задачу: пусть требуется поддерживать очередь и уметь находить минимум на всём её содержимом за $O(1)$.

Здесь используется та же идея, что и в стеке с минимумом. Мы будем хранить в каждом стеке не просто значения, а пары: значение и минимум на всём стеке.

То есть и $s_1$, и $s_2$ — это стеки с поддержкой минимума.

Как тогда получить минимум на всей очереди?

Очередь состоит из двух частей:

* элементы, которые лежат в $s_2$ (они находятся ближе к началу очереди),
* элементы, которые лежат в $s_1$ (они добавлены позже).

Минимум на всей очереди — это минимум из:

* минимума в $s_1$,
* минимума в $s_2$.

Если один из стеков пуст, берём минимум из другого.

Таким образом, все операции очереди (добавление, удаление, получение минимума) выполняются за $O(1)$ амортизированно.

Ниже приведена реализация на C++.

```cpp

struct QueueMin {
    StackMin s1, s2;

    bool empty() const {
        return s1.empty() && s2.empty();
    }

    void push(int x) {
        s1.push(x);
    }

    void move() {
        if (s2.empty()) {
            while (!s1.empty()) {
                int x = s1.top();
                s1.pop();
                s2.push(x);
            }
        }
    }

    void pop() {
        move();
        if (s2.empty()) {
            throw runtime_error("Queue is empty");
        }
        s2.pop();
    }

    int front() {
        move();
        if (s2.empty()) {
            throw runtime_error("Queue is empty");
        }
        return s2.top();
    }

    int get_min() {
        if (s1.empty() && s2.empty()) {
            throw runtime_error("Queue is empty");
        }
        if (s1.empty()) return s2.get_min();
        if (s2.empty()) return s1.get_min();
        return min(s1.get_min(), s2.get_min());
    }
};
```

Здесь снова используется уже знакомый приём: каждая структура хранит не только сами элементы, но и агрегированную информацию (минимум), которая обновляется локально. За счёт этого удаётся поддерживать более сложные операции, не теряя линейной эффективности.

Рассмотрим теперь классическую задачу, в которой очередь с поддержкой минимума возникает естественным образом.

Пусть дан массив $a_0, a_1, \dots, a_{n-1}$ и фиксированное число $k$. Требуется для каждого подотрезка длины $k$, то есть для каждого окна

$$
[i,, i + k)
$$

найти минимум элементов на этом отрезке.

Если решать задачу напрямую, для каждого окна пересчитывая минимум, получим $O(nk)$, что в худшем случае даёт $O(n^2)$. Попробуем использовать идею «скользящего окна» и поддерживать минимум при сдвиге окна.

Заметим, что при переходе от окна $[i, i+k)$ к окну $[i+1, i+k+1)$:

* из окна уходит элемент $a_i$,
* в окно добавляется элемент $a_{i+k}$.

То есть окно меняется «локально», и нет смысла пересчитывать минимум с нуля.

Будем поддерживать текущее окно с помощью очереди с минимумом. Эта структура позволяет:

* добавлять элемент в конец,
* удалять элемент из начала,
* получать минимум по всей структуре,

всё за $O(1)$ амортизированно.

Идея алгоритма следующая.

Будем идти по массиву слева направо и поддерживать очередь, которая всегда содержит элементы текущего окна.

На шаге $i$:

* добавляем элемент $a_i$ в очередь,
* если размер окна стал больше $k$, удаляем элемент, который вышел из окна (это $a_{i-k}$),
* если $i \ge k-1$, то текущее окно $[i-k+1, i+1)$ уже полностью сформировано, и можно взять минимум.

То есть на каждом шаге мы:

* расширяем окно справа,
* при необходимости сдвигаем его слева,
* читаем минимум.

Почему это работает эффективно?

Очередь с минимумом устроена так, что она хранит элементы в двух стеках с минимумом. Минимум всей очереди в любой момент равен минимуму из минимумов этих стеков. Добавление и удаление элементов происходят за амортизированное $O(1)$, поэтому весь алгоритм работает за $O(n)$.

Важно также понять, почему мы вообще можем использовать такую структуру. При сдвиге окна мы всегда удаляем элемент, который раньше всех был добавлен. Это ровно поведение очереди. При этом нам нужно знать минимум по всем текущим элементам — и это как раз та дополнительная информация, которую структура поддерживает.

Таким образом, задача о минимуме на каждом окне длины $k$ естественно сводится к поддержанию очереди с дополнительной операцией получения минимума, а итоговая сложность становится линейной.

## Дек

Теперь рассмотрим дек.

Дек (двусторонняя очередь) — это линейная структура данных, в которой операции добавления и удаления допускаются с обоих концов. То есть, в отличие от стека и очереди, здесь нет «привилегированного» конца: можно работать как с началом, так и с концом структуры.

Обычно у дека есть следующие операции:

* добавить элемент в конец,
* удалить элемент из конца,
* добавить элемент в начало,
* удалить элемент из начала,
* получить элементы на концах.

Все эти операции должны выполняться за $O(1)$.

С точки зрения реализации дек можно рассматривать как обобщение очереди. Например, его можно реализовать на массиве, используя два указателя — на начало и конец, — и двигая их по кругу. Такая реализация называется циклическим буфером. В ней элементы хранятся в массиве, но индексы «оборачиваются» по модулю размера массива, поэтому ни сдвигов, ни перераспределений не требуется.

Однако в контексте алгоритмов дек интересен не столько как структура сам по себе, сколько как инструмент для поддержания информации на подотрезке.

Вспомним задачу поиска минимума в окне. Ранее мы обсуждали решение через очередь с поддержкой минимума. Оно хорошо показывает саму идею: окно двигается, из него один элемент уходит, другой приходит, а мы хотим быстро поддерживать агрегированную характеристику. Однако для задачи минимума в окне существует более специальный и более изящный инструмент — дек.

Чтобы понять, почему здесь вообще появляется дек, вернёмся к самой задаче.

Пусть дан массив $a_0, a_1, \dots, a_{n-1}$ и число $k$. Для каждого окна длины $k$, то есть для каждого подотрезка

$$
[i,, i+k),
$$

нужно найти минимум.

Если считать минимум в каждом окне независимо, получится $O(nk)$. Решение через очередь с поддержкой минимума уже даёт линейное время. Но в этой конкретной задаче можно пойти ещё дальше и хранить не все элементы окна, а только те, которые действительно могут претендовать на роль минимума.

В этом и состоит основная идея решения через дек.

Будем хранить в деке не сами значения, а индексы элементов массива. Это важно по двум причинам. Во-первых, по индексу всегда можно получить само значение $a_i$. Во-вторых, именно по индексу удобно понимать, не вышел ли элемент из текущего окна.

Теперь разберёмся, какие индексы вообще имеет смысл хранить.

Предположим, что в деке уже лежат некоторые индексы, и мы хотим добавить новый индекс $i$. Пока в конце дека находится индекс $j$, для которого

$$
a_j \ge a_i,
$$

индекс $j$ можно удалить.

Почему это корректно? Потому что элемент $a_j$ не меньше нового элемента $a_i$, но расположен левее. Значит, для всех будущих окон, в которые попадут оба элемента, индекс $j$ заведомо хуже индекса $i$: он не даёт меньшего значения и при этом раньше выйдет из окна. Следовательно, $j$ никогда больше не станет минимумом, и хранить его нет смысла.

После удаления всех таких индексов мы добавляем $i$ в конец дека.

Таким образом, индексы в деке всегда хранятся так, что соответствующие им значения строго возрастают:

$$
a_{d_0} < a_{d_1} < a_{d_2} < \dots
$$

где $d_0, d_1, d_2, \dots$ — индексы в деке слева направо.

Отсюда сразу следует важный вывод: минимум текущего окна всегда находится в начале дека. Действительно, там стоит индекс с наименьшим значением среди всех сохранённых кандидатов.

Но одного этого недостаточно. Нужно ещё следить, чтобы индексы в деке действительно принадлежали текущему окну. Когда окно сдвигается вправо, некоторые старые элементы выходят из него слева. Если индекс в начале дека больше не лежит в окне, его нужно удалить из начала.

Итак, при переходе к очередному элементу $a_i$ выполняются две операции.

Сначала удаляем из начала дека все индексы, которые уже не принадлежат текущему окну. Для окна длины $k$, оканчивающегося в позиции $i$, текущее окно имеет вид

$$
[i-k+1,, i+1).
$$

Поэтому индекс $j$ нужно удалить из начала дека, если

$$
j < i-k+1.
$$

После этого удаляем из конца дека все индексы, соответствующие элементам, не меньшим $a_i$, и затем добавляем индекс $i$ в конец.

Когда $i \ge k-1$, окно уже набрало длину $k$, и минимумом на нём будет элемент с индексом, стоящим в начале дека.

Полезно ещё раз отдельно понять, почему всё это работает.

Дек хранит не все элементы окна, а только «кандидатов на минимум». Если некоторый элемент оказался не меньше более нового элемента, то он уже никогда не сможет стать минимумом в будущем и удаляется сразу. Поэтому в деке остаются только те индексы, которые ещё могут оказаться полезными.

С другой стороны, если какой-то индекс вышел за левую границу окна, его тоже больше нельзя использовать, и он удаляется из начала.

Таким образом, в любой момент в деке остаются ровно те элементы, которые одновременно:

* ещё лежат в текущем окне;
* не были «доминированы» более выгодными элементами справа.

Первый элемент дека среди них имеет наименьшее значение, а значит, и является минимумом окна.

```cpp
#include <iostream>
#include <deque>
#include <vector>

using namespace std;

vector<int> window_minimum(const vector<int>& a, int k) {
    deque<int> dq;
    vector<int> ans;

    for (int i = 0; i < (int)a.size(); i++) {
        while (!dq.empty() && dq.front() <= i - k) {
            dq.pop_front();
        }

        while (!dq.empty() && a[dq.back()] >= a[i]) {
            dq.pop_back();
        }

        dq.push_back(i);

        if (i >= k - 1) {
            ans.push_back(a[dq.front()]);
        }
    }

    return ans;
}
```

Разберём, что здесь происходит по шагам.

В начале каждой итерации мы удаляем из начала дека индексы, которые уже вышли из окна. Условие

```cpp
dq.front() <= i - k
```

эквивалентно тому, что индекс больше не принадлежит окну $[i-k+1,, i+1)$.

Затем удаляем из конца дека все индексы элементов, не меньших текущего. После этого добавляем текущий индекс.

Наконец, если окно уже имеет длину $k$, то минимумом будет элемент с индексом `dq.front()`.

Осталось понять оценку сложности. Каждый индекс добавляется в дек ровно один раз. Из дека он тоже удаляется не более одного раза: либо из начала, когда выходит из окна, либо из конца, когда вытесняется более выгодным элементом. Поэтому суммарное число операций с деком линейно, и весь алгоритм работает за $O(n)$.
